# Transition `crabslab` from Rust-GPU/SPIR-V to `wgsl-rs`

**Date:** 2026-02-14

## Overview

This plan transitions the crabslab workspace from Rust-GPU (`spirv-std`, SPIR-V
compilation, `cargo-gpu`) to `wgsl-rs` (proc-macro-based Rust-to-WGSL
transpilation). The core abstraction changes from trait-based generics
(`SlabItem`, `Slab`) to macro-based code generation (`#[slab_module]`,
`#[slab_item]`, `read_type_name!`/`write_type_name!` macros).

## Key Architectural Decisions

1. **`Id<T>` is removed.** Replaced by per-type concrete ID structs (e.g.,
   `DataId { inner: u32 }`) generated by `#[slab_item]`.
2. **Old `SlabItem` trait is replaced** by a new CPU-only `SlabItem` trait with
   an associated `Id` type, auto-implemented by `#[slab_module]`.
3. **Old `Slab` and `GrowableSlab` traits are removed.**
4. **Slab read/write uses inline macro expansion.** Per-type macros
   (`read_data!`, `write_data!`) expand to inline slab access code in both Rust
   and WGSL, avoiding the WGSL restriction on passing storage pointers to
   functions.
5. **`#[slab_module]`** is a proc-macro that processes `#[slab_item]`
   annotations, generates ID types + read/write macros + CPU trait impls, then
   replaces itself with `#[wgsl]` so wgsl-rs transpiles the module to WGSL.
6. **wgpu integration** uses wgsl-rs's `linkage-wgpu` feature for
   auto-generated shader modules, bind group layouts, and pipeline helpers.

## Phase 0: Prerequisites -- wgsl-rs Changes

Before crabslab migration can proceed, some wgsl-rs features may need extending.

### 0.1 Verify `macro_rules!` inside `#[wgsl]` modules

The generated `read_data!` / `write_data!` macros need to be defined inside
`#[wgsl]` modules and survive transpilation. Since `#[wgsl]` is "strictly
additive" and preserves all Rust code, `macro_rules!` definitions should pass
through unchanged. The WGSL code gen would need to **skip** macro definitions
(they have no WGSL equivalent). **Verify this works or add `macro_rules!`
passthrough support to wgsl-rs.**

### 0.2 Verify `as usize` indexing pattern

The inline expansion uses `slab[idx as usize]` where `idx` is `u32`. Confirm
that `as usize` indexing works in `#[wgsl]` modules (it should -- wgsl-rs maps
`usize` to `u32`).

### 0.3 Verify cross-module macro imports

`read_data!` macros defined in one `#[wgsl]` module need to be usable in
another via `use super::data_module::*`. Since `macro_rules!` macros are
exported with `#[macro_export]` or by being `pub`, verify glob imports of macros
work across `#[wgsl]` module boundaries.

**Estimated effort:** 1-3 days of investigation/fixes in wgsl-rs.

## Phase 1: New `#[slab_module]` Proc-Macro (in `crabslab-derive`)

Repurpose `crates/crabslab-derive` to contain the `#[slab_module]` attribute
macro alongside (initially) the existing `#[derive(SlabItem)]`.

### 1.1 `#[slab_module]` macro behavior

**Input:** A Rust module annotated with `#[slab_module]`:

```rust
#[slab_module]
pub mod data_types {
    use wgsl_rs::std::*;

    #[slab_item]
    pub struct Data {
        pub i: u32,
        pub float_val: f32,
        pub ints_0: u32,
        pub ints_1: u32,
    }
}
```

**Output:** The macro rewrites the module to:

```rust
#[wgsl]
pub mod data_types {
    use wgsl_rs::std::*;

    pub struct Data {
        pub i: u32,
        pub float_val: f32,
        pub ints_0: u32,
        pub ints_1: u32,
    }

    // --- Generated ID type ---

    pub struct DataId {
        pub inner: u32,
    }

    impl DataId {
        pub const NONE: DataId = DataId { inner: 4294967295u32 };
        pub const ZERO: DataId = DataId { inner: 0u32 };

        pub fn new(index: u32) -> DataId {
            DataId { inner: index }
        }

        pub fn is_none(id: DataId) -> bool {
            id.inner == 4294967295u32
        }
    }

    // --- Generated array type ---

    pub struct DataArray {
        pub id: DataId,
        pub len: u32,
    }

    impl DataArray {
        pub const NONE: DataArray = DataArray {
            id: DataId::NONE,
            len: 0u32,
        };

        pub fn at(arr: DataArray, index: u32) -> DataId {
            if index >= arr.len {
                DataId::NONE
            } else {
                DataId::new(arr.id.inner + DATA_SLAB_SIZE * index)
            }
        }
    }

    // --- Generated constants ---

    pub const DATA_SLAB_SIZE: u32 = 4u32;

    // --- Generated read/write macros ---

    macro_rules! read_data {
        ($id:expr, $slab:expr) => {{
            let __slab = $slab;
            let __idx = $id.inner;
            Data {
                i: __slab[__idx as usize],
                float_val: bitcast_f32(__slab[(__idx + 1u32) as usize]),
                ints_0: __slab[(__idx + 2u32) as usize],
                ints_1: __slab[(__idx + 3u32) as usize],
            }
        }};
    }

    macro_rules! write_data {
        ($data:expr, $id:expr, $slab:expr) => {{
            let __slab = $slab;
            let __data = $data;
            let __idx = $id.inner;
            __slab[__idx as usize] = __data.i;
            __slab[(__idx + 1u32) as usize] = bitcast_u32(__data.float_val);
            __slab[(__idx + 2u32) as usize] = __data.ints_0;
            __slab[(__idx + 3u32) as usize] = __data.ints_1;
        }};
    }
}

// --- Generated OUTSIDE the #[wgsl] module (CPU-only trait impl) ---

impl crabslab::SlabItem for data_types::Data {
    type Id = data_types::DataId;
    const SLAB_SIZE: u32 = 4;

    fn slab_read(slab: &[u32], index: u32) -> Self {
        data_types::Data {
            i: slab[index as usize],
            float_val: f32::from_bits(slab[(index + 1) as usize]),
            ints_0: slab[(index + 2) as usize],
            ints_1: slab[(index + 3) as usize],
        }
    }

    fn slab_write(data: &Self, slab: &mut [u32], index: u32) {
        slab[index as usize] = data.i;
        slab[(index + 1) as usize] = data.float_val.to_bits();
        slab[(index + 2) as usize] = data.ints_0;
        slab[(index + 3) as usize] = data.ints_1;
    }
}
```

### 1.2 Type mapping rules for slab read/write

| Rust Field Type | Slab Size | Read Expression (WGSL) | Write Expression (WGSL) |
|---|---|---|---|
| `u32` | 1 | `slab[idx]` | `slab[idx] = val` |
| `i32` | 1 | `bitcast_i32(slab[idx])` | `slab[idx] = bitcast_u32(val)` |
| `f32` | 1 | `bitcast_f32(slab[idx])` | `slab[idx] = bitcast_u32(val)` |
| `bool` | 1 | `slab[idx] != 0u32` | `slab[idx] = if val { 1u32 } else { 0u32 }` |
| `Vec2f` | 2 | `vec2f(bitcast_f32(slab[idx]), ...)` | 2 component writes |
| `Vec3f` | 3 | `vec3f(bitcast_f32(slab[idx]), ...)` | 3 component writes |
| `Vec4f` | 4 | `vec4f(bitcast_f32(slab[idx]), ...)` | 4 component writes |
| `Vec2u` / `Vec3u` / `Vec4u` | 2/3/4 | `vec2u(slab[idx], ...)` | component writes |
| `Vec2i` / `Vec3i` / `Vec4i` | 2/3/4 | `vec2i(bitcast_i32(slab[idx]), ...)` | component writes |
| Nested `#[slab_item]` struct | That type's SLAB_SIZE | `read_inner_type!(InnerTypeId::new(idx), slab)` | `write_inner_type!(val, InnerTypeId::new(idx), slab)` |
| `#[repr(u32)]` `#[slab_item]` enum | 1 (discriminant) | `read_enum_type!(EnumTypeId::new(idx), slab)` | `write_enum_type!(val, EnumTypeId::new(idx), slab)` |
| Tuple struct `Foo(pub u32)` | inner type's size | Same as inner type | Same as inner type |

### 1.3 Enum support

For `#[repr(u32)]` enums annotated with `#[slab_item]`:

```rust
#[slab_item]
#[repr(u32)]
pub enum DataChangeTy {
    I = 0,
    Float = 1,
    Ints = 2,
}
```

Generates:
- `DataChangeTyId { inner: u32 }`
- `DATA_CHANGE_TY_SLAB_SIZE: u32 = 1`
- `read_data_change_ty!` / `write_data_change_ty!` macros that read/write the
  discriminant as a `u32`

When a struct field has a `#[repr(u32)]` enum type, the generated read macro
reads a `u32` from the slab and the Rust side reconstructs the enum. In WGSL,
the enum is represented as integer constants, so the field is effectively `u32`.

### 1.4 Tuple struct / primitive wrapper support

`#[slab_item]` supports tuple structs wrapping primitives:

```rust
#[slab_item]
pub struct InvocationCount(pub u32);
```

Generates:
- `InvocationCountId { inner: u32 }`
- `INVOCATION_COUNT_SLAB_SIZE: u32 = 1`
- `read_invocation_count!` / `write_invocation_count!` macros

This allows typed IDs for primitive slab entries.

### 1.5 Array type generation

Every `#[slab_item]` type gets a corresponding array type:

```rust
pub struct DataArray {
    pub id: DataId,
    pub len: u32,
}

impl DataArray {
    pub const NONE: DataArray = DataArray {
        id: DataId::NONE,
        len: 0u32,
    };

    pub fn at(arr: DataArray, index: u32) -> DataId {
        if index >= arr.len {
            DataId::NONE
        } else {
            DataId::new(arr.id.inner + DATA_SLAB_SIZE * index)
        }
    }
}
```

The array type also gets its own read/write macros (`read_data_array!`,
`write_data_array!`) since `DataArray` is itself a 2-element slab item
(`id.inner: u32` + `len: u32`).

### 1.6 Naming conventions

| Generated Item | Naming Pattern | Example |
|---|---|---|
| ID type | `{TypeName}Id` | `DataId` |
| Array type | `{TypeName}Array` | `DataArray` |
| Slab size constant | `{TYPE_NAME}_SLAB_SIZE` | `DATA_SLAB_SIZE` |
| Read macro | `read_{type_name}!` | `read_data!` |
| Write macro | `write_{type_name}!` | `write_data!` |

All generated macro names use snake_case to ensure uniqueness when imported via
glob across modules.

## Phase 2: New `SlabItem` Trait (CPU-only, in `crabslab`)

### 2.1 Define the new trait

In `crates/crabslab/src/lib.rs` (outside any `#[wgsl]` module):

```rust
/// CPU-only trait for types that can be stored in a u32 slab.
///
/// Auto-implemented by the `#[slab_module]` macro for `#[slab_item]` types.
pub trait SlabItem: Sized {
    /// The concrete ID type for this slab item (e.g. `DataId`).
    type Id: Copy + Default;

    /// The number of `u32` slots this type occupies in a slab.
    const SLAB_SIZE: u32;

    /// Read this type from a `u32` slab at the given index.
    fn slab_read(slab: &[u32], index: u32) -> Self;

    /// Write this type into a `u32` slab at the given index.
    fn slab_write(data: &Self, slab: &mut [u32], index: u32);

    /// Serialize this value into a new `Vec<u32>`.
    fn slab_data(&self) -> Vec<u32> {
        let mut data = vec![0u32; Self::SLAB_SIZE as usize];
        Self::slab_write(self, &mut data, 0);
        data
    }
}
```

### 2.2 Implement for primitives

Manual `SlabItem` impls for `u32`, `i32`, `f32`, `bool`, and glam vector/matrix
types. These live in `crabslab` and don't need `#[slab_item]`. Each primitive
gets a simple ID type (or uses a generic `SlabIndex { inner: u32 }`).

### 2.3 Remove old types and traits

- Remove old `Slab` trait
- Remove old `SlabItem` trait
- Remove old `GrowableSlab` trait
- Remove generic `Id<T>` and `Array<T>`
- Remove `CpuSlab<B>` wrapper (or repurpose if still useful)
- Remove all `spirv-std` dependencies
- Remove all `#[cfg(target_arch = "spirv")]` / `#[cfg(not(target_arch = "spirv"))]` blocks
- Remove `#![cfg_attr(target_arch = "spirv", no_std)]` from all crates
- Remove `spirv-std` from workspace dependencies
- Remove `[patch.crates-io]` spirv-std entry
- Remove helper functions: `slice_index`, `array_index`, `array_index_mut`,
  `__saturating_sub`

## Phase 4: Migrate Wire Types (`craballoc-test-wire-types`)

### 4.1 Rewrite as `#[slab_module]`

```rust
#[slab_module]
pub mod wire_types {
    use wgsl_rs::std::*;

    #[slab_item]
    pub struct Data {
        pub i: u32,
        pub float_val: f32,
        pub ints_0: u32,
        pub ints_1: u32,
    }

    #[slab_item]
    #[repr(u32)]
    pub enum DataChangeTy {
        I = 0,
        Float = 1,
        Ints = 2,
    }

    #[slab_item]
    pub struct DataChange {
        pub ty: DataChangeTy,
        pub data_0: u32,
        pub data_1: u32,
        pub data_2: u32,
    }

    impl DataChange {
        #[wgsl_allow(non_literal_match_statement_patterns)]
        pub fn apply(change: DataChange, data: Data) -> Data {
            match change.ty {
                DataChangeTy::I => Data {
                    i: change.data_0,
                    float_val: data.float_val,
                    ints_0: data.ints_0,
                    ints_1: data.ints_1,
                },
                DataChangeTy::Float => Data {
                    i: data.i,
                    float_val: bitcast_f32(change.data_0),
                    ints_0: data.ints_0,
                    ints_1: data.ints_1,
                },
                _ => Data {
                    i: data.i,
                    float_val: data.float_val,
                    ints_0: change.data_0,
                    ints_1: change.data_1,
                },
            }
        }
    }

    #[slab_item]
    pub struct ArrayChange {
        pub i: u32,
        pub change: DataChange,
    }

    #[slab_item]
    pub struct AnyChangeId {
        pub change_id: ArrayChangeId,
        pub data_array: DataArray,
    }

    #[slab_item]
    pub struct InvocationCount(pub u32);

    #[slab_item]
    pub struct ApplyDataChangeInvocation {
        pub changes_ids: AnyChangeIdArray,
        pub invocations_id: InvocationCountId,
        pub invocations_skipped_id: InvocationCountId,
    }
}
```

### 4.2 Tuple flattening

Current code uses tuples like `(u32, u32)` for `Data.ints`. WGSL has no tuples.
These are flattened to `ints_0: u32, ints_1: u32`.

### 4.3 CPU-only helpers

CPU-only code (like `Display` impls, `DataChange::new()` constructors that use
`SlabItem` generics) lives **outside** the `#[slab_module]` module:

```rust
// Outside the #[wgsl] module -- CPU-only
impl core::fmt::Display for wire_types::DataChange {
    fn fmt(&self, f: &mut core::fmt::Formatter<'_>) -> core::fmt::Result {
        // ...
    }
}
```

### 4.4 Atomic operations

The current `spirv_std::arch::atomic_i_increment` for invocation counting is
replaced with wgsl-rs's `atomic_add`. This may require a separate
`Atomic<u32>` storage variable or a workgroup variable, since atomics on
arbitrary indices within a `RuntimeArray<u32>` are not directly supported in
WGSL.

Options:
- Use a separate `storage!(group(0), binding(2), read_write, COUNTERS: Counters)`
  where `Counters` contains `Atomic<u32>` fields
- Use `workgroup!` variables for workgroup-scoped atomic counters

**Estimated effort:** 3-4 days

## Phase 5: Migrate Compute Shader (`craballoc-test-shaders`)

### 5.1 Rewrite as `#[wgsl]` compute shader

The `craballoc-test-shaders` crate becomes a regular Rust crate (no
`#![no_std]`, no `spirv-std`):

```rust
#[slab_module]
pub mod apply_data_changes {
    use wgsl_rs::std::*;
    use super::wire_types::*;

    storage!(group(0), binding(0), read_write, DATA_SLAB: RuntimeArray<u32>);
    storage!(group(0), binding(1), CHANGES_SLAB: RuntimeArray<u32>);

    #[compute]
    #[workgroup_size(16, 1, 1)]
    pub fn main(#[builtin(global_invocation_id)] global_id: Vec3u) {
        let invocation = read_apply_data_change_invocation!(
            ApplyDataChangeInvocationId::ZERO,
            get!(CHANGES_SLAB)
        );
        let index = global_id.x();

        if index >= invocation.changes_ids.len {
            return;
        }

        let change_info = read_any_change_id!(
            AnyChangeIdArray::at(invocation.changes_ids, index),
            get!(CHANGES_SLAB)
        );

        let change = read_array_change!(change_info.change_id, get!(CHANGES_SLAB));
        let data_id = DataArray::at(change_info.data_array, change.i);
        let data = read_data!(data_id, get!(DATA_SLAB));
        let new_data = DataChange::apply(change.change, data);
        write_data!(new_data, data_id, get_mut!(DATA_SLAB));
    }
}
```

### 5.2 Use `linkage-wgpu` for wgpu integration

- `apply_data_changes::linkage::bind_group_0::layout(device)` -- creates
  `wgpu::BindGroupLayout`
- `apply_data_changes::linkage::main::WORKGROUP_SIZE` -- the workgroup size

- Per-binding buffer descriptor helpers

## Open Questions / Risks

### 1. `macro_rules!` inside `#[wgsl]` modules

**Risk: HIGH.** This is the biggest unknown. If wgsl-rs can't handle
`macro_rules!` definitions inside modules (i.e., it tries to parse them as WGSL
and fails), the macro approach needs adjustment. Possible fallback: define
macros **outside** the `#[wgsl]` module and import them, or have `#[slab_module]`
emit macros in a sibling module.

### 2. Cross-crate macro visibility

`read_data!` macros defined in `craballoc-test-wire-types` need to be usable in
`craballoc-test-shaders`. Rust's `macro_rules!` export rules across crate
boundaries are subtle (`#[macro_export]` puts them at crate root, not at module
level). Verify this works with `#[wgsl]` module glob imports.

### 3. `RuntimeArray<u32>` as slab type

Using `RuntimeArray<u32>` (maps to `array<u32>` in WGSL) as the slab type in
storage buffers should work, but verify that indexing via `get!(SLAB)[idx]`
works correctly in both Rust and WGSL, and that `get!()` / `get_mut!()` return
the right types for macro expansion.

### 4. Atomic counter pattern

The current code atomically increments a counter at a specific slab index. In
WGSL, atomics require the `Atomic<T>` type. An `Atomic<u32>` cannot exist at an
arbitrary index within a `RuntimeArray<u32>`. Solutions:
- Separate storage binding with an `Atomic<u32>` struct
- Workgroup-scoped atomic variables
- Drop atomic counting if it's only used for test validation

### 5. Nested macro expansion

When `read_array_change!` internally needs to call `read_data_change!` for the
nested `change: DataChange` field, the generated macros must properly compose.
Verify nested macro invocations expand correctly in both Rust and WGSL contexts.

### 6. `match` as expression vs statement

wgsl-rs transpiles `match` to WGSL `switch`, which is a **statement** not an
expression. `DataChange::apply()` uses `match` with a return value. This may
need to be restructured to use `match` as a statement with explicit variable
assignment:

```rust
let result: Data;
match change.ty {
    DataChangeTy::I => { result = Data { ... }; },
    DataChangeTy::Float => { result = Data { ... }; },
    _ => { result = Data { ... }; },
}
result
```

Or rely on wgsl-rs's implicit-return handling if it supports this pattern.

### 7. Struct update syntax

WGSL has no struct update syntax (`..data`). All struct fields must be
explicitly listed in every construction. The `DataChange::apply()` method
demonstrates this -- each match arm constructs a full `Data` with all fields.
