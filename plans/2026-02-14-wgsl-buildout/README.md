# Transition `crabslab` from Rust-GPU/SPIR-V to `wgsl-rs`

**Date:** 2026-02-14
**Revised:** 2026-02-26

## Overview

This plan transitions the crabslab workspace from Rust-GPU (`spirv-std`, SPIR-V
compilation, `cargo-gpu`) to `wgsl-rs` (proc-macro-based Rust-to-WGSL
transpilation). The core abstraction changes from trait-based generics
(`SlabItem`, `Slab`) to function-based serialization (`#[slab_module]`,
`#[slab_item]`, per-type `*_from_array`/`*_to_array` functions) with wgsl-rs
built-in `slab_read_array!`/`slab_write_array!` macros for storage buffer
access.

## Strategy

Rather than modifying existing crates in place, Phase 1 removes the old crates
(`crabslab`, `crabslab-derive`, `craballoc-test-shaders`,
`craballoc-test-wire-types`) from workspace members and creates new crates
(`crabslab2`, `crabslab2-macros`) from scratch. The old crates remain on disk
for reference but do not compile. `craballoc` is updated in place in Phase 2.
The final cleanup phase renames `crabslab2` to `crabslab` and deletes the old
crates.

## Key Architectural Decisions

1. **`Id<T>` is removed.** Replaced by per-type concrete ID structs (e.g.,
   `DataId { inner: u32 }`) generated by `#[slab_item]`. On the CPU side, slab
   indices are raw `u32`; the `SlabItem` trait has no associated ID type.
2. **Old `SlabItem` trait is replaced** by a new `SlabItem` trait in `crabslab2`
   with an associated `type Array` and `to_array`/`from_array` methods.
   Auto-implemented by `#[slab_module]`.
3. **Old `Slab`, `GrowableSlab`, `CpuSlab`, generic `Id<T>`, and `Array<T>`
   are removed.**
4. **Slab read/write is separated into two layers:**
   - **Storage buffer access:** wgsl-rs built-in `slab_read_array!`/`slab_write_array!`
     statement macros copy `[u32; N]` arrays between storage buffers and local
     variables. These are generic (not per-type) and emit WGSL `for` loops.
   - **Struct (de)serialization:** Per-type `*_from_array`/`*_to_array`
     functions generated by `#[slab_item]` convert between `[u32; N]` arrays
     and the struct type. These cross module boundaries as normal WGSL functions.
   This two-layer approach avoids the WGSL restriction on passing storage
   pointers to user-defined functions and avoids needing `macro_rules!`
   invocations inside `#[wgsl]` modules (which wgsl-rs rejects in expression
   position).
5. **`#[slab_module]`** is a proc-macro that processes `#[slab_item]`
   annotations, generates ID types + `*_from_array`/`*_to_array` functions +
   CPU trait impls, then replaces itself with `#[wgsl]` so wgsl-rs transpiles
   the module to WGSL.
6. **wgpu integration** uses wgsl-rs's `linkage-wgpu` feature for
   auto-generated shader modules, bind group layouts, and pipeline helpers.
7. **No backward compatibility.** The old crates are removed from the workspace
   immediately. No coexistence period, no bridging types.
8. **No tuple `SlabItem` impls.** Tuples are not supported as slab items.
9. **No glam `SlabItem` impls.** Users use wgsl-rs's built-in vector/matrix
   types instead.

## Success Criteria

1. All existing `craballoc` tests pass with the wgsl-rs backend
2. Generated WGSL validates via naga at compile time or test time
3. CPU-side types from `#[slab_module]` modules implement the new `SlabItem`
   trait and work with `Arena`
4. No Rust-GPU, SPIR-V, or `spirv-std` dependencies remain
5. Human-readable WGSL output for debugging
6. The `#[slab_item]` annotation generates correct ID types, array types,
   `*_from_array`/`*_to_array` functions, and slab size constants for structs,
   tuple structs, and `#[repr(u32)]` enums
7. `slab_read_array!`/`slab_write_array!` macros work in both Rust (CPU-side)
   and WGSL (GPU-side) contexts

## Open Questions / Risks

### Resolved Risks

1. **`macro_rules!` inside `#[wgsl]` modules** -- RESOLVED. Definitions pass
   through, but invocations in expression position are rejected. Moot because
   we use plain functions instead of per-type macros.
2. **Cross-crate macro visibility** -- RESOLVED. Normal cross-crate function
   imports (`use super::wire_types::*`) replace `macro_rules!` exports.
3. **`RuntimeArray<u32>` as slab type** -- LOW RISK (confirmed working).
4. **Nested macro expansion** -- RESOLVED. Nested types use nested
   `*_from_array` function calls with element-by-element array construction.
5. **`slab_read_array!`/`slab_write_array!` implementation** -- RESOLVED.
   Implemented in wgsl-rs commit `420998a`.
6. **Coexistence with old crates** -- RESOLVED. No coexistence. Old crates
   removed from workspace; new crates built from scratch.

### Remaining Risks

- **Atomic counter pattern** -- LOW RISK. Full atomic support in wgsl-rs.
  Requires a separate storage binding (cannot use `Atomic<u32>` at arbitrary
  index within `RuntimeArray<u32>`).
- **`match` as expression vs statement** -- HIGH RISK (confirmed). Must use
  statement form with explicit variable assignment. Same applies to `if` as
  expression.
- **Struct update syntax** -- CONFIRMED. WGSL has no `..data` syntax; all
  fields must be listed explicitly.
- **Nested `from_array` verbosity** -- LOW RISK. Verbose but correct; generated
  code, not hand-written.
- **Method receiver syntax** -- LOW RISK. Must use `Type::method(obj, args)`
  instead of `obj.method(args)`.
- **No generics in WGSL** -- LOW RISK. Each function is concrete; macros handle
  the generic storage access layer.
